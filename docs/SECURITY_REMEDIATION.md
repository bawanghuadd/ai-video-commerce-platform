# 安全修复与授权实施计划

> 更新日期：2026-07-13  
> 范围：Phase 1 最小安全补丁与后续授权设计  
> 原则：不修改现有数据库数据，不实施未经确认的完整 RBAC

## 1. Phase 1 已实施补丁

- 应用启动默认不执行 `Base.metadata.create_all()`。
- 应用启动默认不打开种子数据 Session。
- 删除源码中的固定 `admin/123456` 管理员初始化行为。
- 开发建表、管理员种子和系统设置种子均由独立环境开关控制，默认关闭。
- 生产环境配置校验禁止启用自动建表或种子写入。
- 管理员种子必须显式提供用户名和至少 12 位密码；不自动重置已存在账号。
- 增加安全 `.env.example`，未提交真实 `.env` 或凭据。
- 增加不访问真实数据库的配置、启动门禁、JWT、密码和 Schema 测试。

这些补丁不会删除、更新或迁移现有数据库中的账号、表和业务数据。已经使用过的历史密码、数据库密码或 JWT Secret 是否泄露无法仅靠代码判断；若真实凭据曾进入公开提交、日志或共享渠道，必须由管理员在外部系统人工轮换。

## 2. 当前权限矩阵

当前后端实际只区分“未认证”和“已认证”，`User.role` 尚未形成强制授权策略。

| 资源 | 未认证 | 任意已认证用户 | admin 专属校验 |
|---|---:|---:|---:|
| 登录、注册 | 允许 | 允许 | 无 |
| 当前用户 `/auth/me` | 拒绝 | 读取自己 | 无 |
| 商品读取/写入/删除 | 拒绝 | 全部允许 | 无 |
| 内容拆解读取/写入/删除 | 拒绝 | 全部允许 | 无 |
| 脚本分镜读取/写入/删除 | 拒绝 | 全部允许 | 无 |
| 视频任务读取/写入/删除 | 拒绝 | 全部允许 | 无 |
| 知识库读取/写入/删除/引用计数 | 拒绝 | 全部允许 | 无 |
| 系统设置读取/修改 | 拒绝 | 全部允许 | 无 |

最高优先级风险是任意注册用户可修改系统设置和删除全部业务资源。

## 3. 建议目标角色

角色语义需要产品负责人确认后再实现：

| 角色 | 建议权限 |
|---|---|
| `admin` | 用户与角色管理、系统设置、全部业务读写、审计查看 |
| `manager` | 全部业务读写、审核与发布；默认不可管理账号和安全设置 |
| `editor` | 商品、内容、脚本、视频、知识库读写；不可修改全局系统设置 |
| `viewer` | 业务只读 |

当前数据库已有 `admin`、`user` 等自由字符串，前端还展示 `manager`，但没有正式角色枚举、权限表、租户/团队或数据所有权语义。因此 Phase 1 不直接把 `user` 映射为某个新角色，也不实施可能锁死现有用户的不完整授权。

## 4. 应当限制的写接口

建议按以下顺序增加服务端依赖校验：

1. `PUT /api/system-settings`：仅 `admin`。
2. 用户和角色管理端点（未来新增）：仅 `admin`。
3. 商品、内容拆解、脚本、视频、知识库的 POST/PUT/DELETE：`admin/manager/editor`。
4. 审核、发布、归档类状态变更：`admin/manager`，是否允许 editor 需产品确认。
5. 所有 GET：已认证角色默认可读；若引入租户/团队，必须再按数据范围过滤。

隐藏前端按钮不能代替后端授权。

## 5. 管理员角色定义

建议将管理员定义为“可管理全局安全与系统配置的高权限角色”，而不是普通业务编辑者。管理员操作至少应记录：

- 操作用户 ID、角色和请求 ID。
- 资源类型、资源 ID、动作和结果。
- 时间、来源 IP（遵循可信代理配置）和失败原因。
- 系统设置变更前后摘要，但不得记录密码、Token、Secret 或完整敏感请求体。

## 6. 403 响应契约

认证失败使用 401，身份有效但权限不足使用 403。建议保持现有错误风格：

```json
{
  "detail": "当前账号无权执行此操作"
}
```

前端继续通过 `getApiErrorMessage()` 展示服务端 detail，不在请求拦截器统一弹普通业务错误。

## 7. 后续实施顺序

1. 盘点当前数据库真实角色值及活跃用户数量，只读导出统计，不修改数据。
2. 与产品负责人确认角色、资源、动作和数据范围矩阵。
3. 增加角色枚举、权限依赖和完整 401/403 测试。
4. 先保护系统设置写接口，再逐资源保护 POST/PUT/DELETE。
5. 增加前端权限展示，但始终以后端校验为准。
6. 增加审计日志、登录限流、账号停用与必要的会话撤销。
7. 若引入租户/团队，先设计 `tenant_id/team_id/owner_id` 和数据迁移，再启用范围授权。

## 8. 数据迁移需求

- 将现有自由字符串角色映射到确认后的角色集合。
- 为未知角色设置明确迁移策略，禁止静默提升为 admin。
- 如增加 editor/viewer，需要决定现有 `user` 的目标角色。
- 若增加角色表或权限表，使用 Alembic；不得依赖 `create_all()`。
- 上线约束前扫描并修复不合法角色值。
- 迁移前备份并验证 downgrade；权限回滚不得恢复固定弱口令或生产自动建表。

## 9. 风险与回滚

- 直接限制写接口可能导致现有普通用户工作流中断。
- 错误映射 `user -> admin` 会造成权限提升；映射过低会造成业务中断。
- 只做前端控制会形成可绕过的假授权。
- JWT 中携带的 role 可能在角色变更后过期；当前服务端每次请求重新查询用户，应以数据库最新角色为准。
- 授权代码应按资源逐步提交，可回滚单资源依赖；数据角色迁移必须有独立 downgrade。
- 已实施的安全启动门禁不应回滚为固定账号或生产自动建表。

## 10. Phase 2 已实施安全能力

- 服务端集中 admin/editor/viewer RBAC；既有 user 兼容 editor，新注册默认 viewer。
- 业务写接口只允许 admin/editor，系统设置写只允许 admin；viewer 只读。
- 授权使用数据库最新角色，伪造 JWT role claim 测试不能绕过。
- 停用用户 Token 返回 401；有效身份越权返回 403。
- 显式管理员 CLI 从环境读取至少 12 位密码；不开机运行、无固定用户名/弱口令。
- System Settings GET 不再隐式创建数据，只有 PUT 是显式写入。
- 应用启动不自动 migration；Alembic URL 必须显式提供。
- 500 对外通用化；request log 仅含 method/path/status/duration/request-id，不记录 Authorization 或请求体。
- 前端 403 不清理会话，写按钮按集中权限隐藏/禁用；服务端仍是权威。

Phase 2 没有访问真实数据库、没有运行生产 migration、没有创建或晋升真实管理员。真实 MySQL 演练、凭据轮换、登录限流、Token 撤销、审计持久化仍需后续独立实施。
